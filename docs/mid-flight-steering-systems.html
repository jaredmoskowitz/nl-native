NL Native Harness Design

Mid-Flight Steering Systems

Five approaches for course-correcting platform agents during /fan-out when the UI or implementation approach diverges from intent.

The problem: Once /fan-out starts, specs are locked. The only mid-implementation mechanism is contract version bumping, which only covers architectural changes — not "I don't like how this looks" or "wrong approach." If you disagree with the direction any of the three agents (iOS, Android, Backend) are taking, you currently have to stop, update the spec, and re-run the full /propose cycle.
1

Generator-Evaluator Loop

Source: Anthropic's harness design blog

How It Works

A dedicated Evaluator agent runs alongside each platform agent during /fan-out. After every N tasks, the Evaluator boots the app, takes screenshots, navigates key flows via automation (Playwright / Simulator MCP), and scores output against the interaction spec. It returns structured feedback — "navigation hierarchy is 3 levels deep, spec says 2" — and the platform agent course-corrects or pivots.

Adapted to NL Native

The QA Verifier role expands from post-hoc to continuous. It runs after every 2–3 tasks per platform, comparing screenshots and behavior against the interaction spec. If scores trend down, the platform agent gets feedback before digging deeper into a bad direction. You see the Evaluator's reports and can inject your own feedback at the same surface.

Anthropic's key finding: tuning a standalone evaluator to be skeptical is "far more tractable than making a generator critical of its own work."

Trade-offs

ProCon
Catches drift early, before it compounds Doubles token cost per feature (evaluator runs constantly)
Keeps human out of the loop for obvious spec violations — only escalates ambiguity Evaluator needs testable criteria — vague interaction specs produce vague evaluations
You can review evaluator scores async and only intervene when something looks off Adds latency — each eval cycle pauses implementation
Proven at Anthropic: separate evaluation from generation Doesn't help with "I don't like this but can't articulate why" — only catches spec deviations
2

Checkpoint + Revert-and-Refine

Source: Cursor plan mode, LangGraph time-travel

How It Works

Platform agents save named checkpoints at milestone boundaries (after completing navigation, data layer, primary screen, etc.). Each checkpoint includes a git tag, screenshot, and summary of decisions made. When you don't like the direction, you revert to a checkpoint and provide a refined prompt — not a patch on top of bad work, but a clean restart from the last good state with better instructions.

Adapted to NL Native

/fan-out inserts checkpoint gates into each platform's task list. After milestone groups (tasks 1–3, 4–6, 7–9), the agent commits, screenshots, and pauses. You review via /status which now shows checkpoint previews. If you dislike the direction: revert, update the interaction spec, resume.

The key Cursor insight: "A clean restart with a refined plan almost always outperforms patching in-progress work."

Trade-offs

ProCon
Clean — no accumulated context pollution from failed directions Throws away work. Reverting to checkpoint 2 of 5 means re-doing 60% of implementation
Simple mental model — it's just git + spec amendment Doesn't help you articulate what you want differently, only lets you reject what you don't
Both platforms checkpoint independently — revert iOS but keep Android Checkpoint granularity is a design problem. Too few = big reverts. Too many = approval fatigue
Cursor's data shows this produces higher quality than iterative correction Requires the refined spec to be better — if you can't articulate the fix, same problem recurs
3

Mid-Flight Spec Amendment

Source: Contract versioning (existing) + Aider architect/editor separation

How It Works

Instead of re-running the full 7-gate /propose cycle, you issue a scoped spec amendment — like a diff against the current interaction spec. The Architect evaluates blast radius: which platform tasks are affected? Only affected tasks get re-planned. Unaffected completed work stays. The Architect bumps the relevant contract version, and platform agents halt, re-read, and resume — using the mechanism that already exists.

Adapted to NL Native

A new /amend command. You say /amend note-creation "use a bottom sheet instead of a full-screen modal". The UX Designer produces an interaction spec delta. The Architect determines if this is a contract-level change or implementation-level, bumps versions if needed, and calculates which tasks on each platform are impacted. Platform agents invalidate only those tasks and re-execute from the amendment point.

Trade-offs

ProCon
Builds on existing contract versioning — extends, not replaces Blast radius calculation is hard. "Change the nav pattern" might touch every task
Preserves completed work that isn't affected by the change Requires precise amendments — vague feedback ("make it feel lighter") doesn't decompose well
Feels natural — it's how real spec-driven teams work (change orders) Adds state complexity — tasks now have: completed, invalidated, pending-re-execution
Keeps the spec as source of truth — the amendment is the feedback UX Designer re-enters mid-implementation, needs a defined handoff protocol
4

Diverge-and-Select

Source: Original — extends best-of-N with human selection Novel

How It Works

When you flag dissatisfaction, each platform agent generates 2–3 alternative approaches for the specific area of concern — not full reimplementations, but focused alternatives for the contentious piece (e.g., three navigation patterns, three creation flows). Each alternative gets a screenshot, a 2-sentence rationale, and a trade-off note. You pick one. Your selection becomes a binding constraint added to the interaction spec, and implementation continues from that choice.

Why This Is Different

Most steering mechanisms require you to describe what you want. This inverts it — the agents show you options, and you choose. This solves the "I don't like it but can't articulate why" problem, which is the most common form of UI dissatisfaction. Selection is cognitively cheaper than description.

Adapted to NL Native

A /diverge command. You say /diverge ios "the note list feels wrong". The iOS Expert generates 3 alternatives for the note list, each as a minimal working implementation with a screenshot. You pick option B. That choice is recorded as a constraint: "note list uses compact card layout with swipe actions per user selection during diverge-and-select." If the concern applies to both platforms, /diverge all runs it on both.

Trade-offs

ProCon
Solves the hardest problem: user knows something is wrong but can't specify the fix 3x implementation cost for the diverged area (alternatives get thrown away)
Selection is faster than specification — react instead of prescribe Quality depends on agent's design taste, which may be limited
Creates durable constraints with clear provenance Risk of choice paralysis if alternatives are too similar or too different
No existing harness does this — unique competitive advantage Only works for UI/UX concerns. Architectural disagreements need a different mechanism
Preserves no-lateral-comms rule — platforms diverge independently Screenshots require a build step per alternative, adding time
5

Feedforward Harness Evolution

Source: Martin Fowler / Thoughtworks "Harness Engineering"

How It Works

Instead of correcting the current implementation, you improve the system of constraints so the problem doesn't recur. When you see something you don't like, you add a rule to the platform's AGENTS.md or interaction spec templates — not a fix to this feature, but a permanent guide for all future features. The current feature gets rebuilt with the improved harness.

Adapted to NL Native

Your dissatisfaction becomes a new convention. "I don't like how dense the list views are" becomes a rule in platforms/ios/AGENTS.md: "List views shall use minimum 56pt row height with 16pt vertical padding between content groups." Next time /fan-out runs — including a re-run of the current feature — that rule is in the feedforward context. Over time, your harness accumulates your design taste as codified constraints.

Trade-offs

ProCon
Compounds over time — every correction makes all future features better Doesn't fix the current problem quickly — still need to re-run /fan-out
Turns subjective preferences into durable, testable rules Hard to codify aesthetic preferences. "Make it feel premium" doesn't decompose into rules
Harness improvements are version-controlled and reviewable Risk of rule bloat — too many constraints make agents brittle
Custom constraints act as "positive prompt injection" per Anthropic's research Requires abstracting from specific complaint to general rule

Recommended Layering

These systems aren't mutually exclusive. The most robust approach layers them, with each covering a different failure mode:

  • System 3 — /amend as the primary mechanism. Extends what already exists in the harness. For when you know what you want changed.
  • System 4 — /diverge for inarticulate dissatisfaction. Fills a gap no other harness has solved. For when you know something's wrong but can't say why.
  • System 2 — Checkpoints as the safety net. Cheap to add, clean revert when all else fails. For when the direction is fundamentally wrong.
  • System 5 — Harness evolution as the long game. Every correction becomes a permanent improvement. For building up your design taste over time.
System 1 (Evaluator Loop) is powerful but expensive and better suited for unattended runs. Less useful when you're actively watching implementation — consider adding it later for overnight or batch feature builds.
